## 2. Shell / owner / lifecycle audit

Three entry paths are currently distinct:

1. `site/app.html` + `site/app.js`: legacy **real** product. `app.js` constructs controllers, `createWorkstationUiController` initializes synchronously, `bindUi` attaches once, renders/restores, then performs legacy-specific self-checks. It assumes legacy parent DOM / ID order.
2. `site/app-v2.html` + `site/ui-v2/mock-workspace.js`: real M2 presentation behavior with **mock** actions/fixtures, not real Process, Mask, History or Recovery.
3. `site/ui-v2/app.html` + `production-workspace.js`: M2.5 production-safe **empty shell**, with unconnected domain adapters and no real product bootstrap.

Existing building blocks: `shell-registry.js` owns declarative slot names; `workstation-v2.js` creates stable `panel.project/base/mask/process/history` (Base under Project) and `panel.process.{step,recipe,code,diagnostics}`; `view-panel.js` owns `view.{main,mask,three,section}.{header,actions,stage,readout,overlays}`; `domain-adapters.js` exposes `register/prepare/show/hide/destroy`; `overlay-manager.js` is intended portal owner. Confirm four scientific hosts by **runtime node identity**, not by DOM inventory alone.

**Required ownership model for M3:** create shell hosts _before_ the first legacy controller DOM lookup; only one production adapter owns the lifecycle of each content subtree and binds its event callbacks; presentation shell owns navigation/layout only; model, process transaction, Recipe replay, History/Variants, persistence and scientific canvas instances retain their existing owners. Stable panel host and four scientific stage identities must survive mode switches and re-render. Moving a real canvas is allowed if identity/listeners/renderer are preserved; recreating it is not. `workstation-v2.js` uses `root.replaceChildren(workbench)` only on initial mount, while it later replaces navigation / viewbar content; `view-panel.js` replaces action/title nodes; `mock-workspace.js` re-renders mock content. These are **not proof** of stable real scientific child nodes or one-time production binding.

**D1 architectural precondition:** resolve the canonical public `app-v2.html` bootstrap using the production shell/adapters. Do not run both mock and production presenters or mount the legacy workstation in parallel. Preserve both `wafercad.workstation-view-mode.v1` and `wafercad.workstation-split-views.v1` in **sessionStorage**, `html[data-ui=v2]`, and original `app.html`. A route-aware `startup-controller.js` / Welcome transition is reserved to D9; do not implement routing by global string replacement.

### Failures diagnosed and corrected

1. A server started in a different command's network namespace was unreachable. Browser runs were rerun with server and browser under the same command; the new preflight starts its own server. No external-network bypass was used.
2. Full desktop Chrome cannot create its process-singleton Unix socket in this environment. The CDP runner used the installed **headless shell** via a temporary executable wrapper with `--no-sandbox`. This establishes headless Chromium evidence, not desktop Windows Chrome or hardware-GPU acceptance. Wrapper contents: `exec /root/.cache/ms-playwright/chromium_headless_shell-1193/chrome-linux/headless_shell --no-sandbox "$@"`.
3. The existing CDP suite's boot polling dereferenced `document.body.dataset` before navigation had created `body`, aborting with a TypeError. Optional chaining now lets the same readiness predicate retry. All 60 original assertions remain intact and passed after the fix.
4. During development, the new probe tried Overview at 768px where the shell correctly disables it. The probe now follows the authoritative `viewState.compact(window)` policy. It also distinguishes four naturally mounted primary adapters from nine explicitly prepared domain placeholders. No product behavior was changed to satisfy these checks.

### Concrete D1 startup design and decision

Recommended topology for D1 review:

1. Preserve `app.html` as the legacy product; keep an explicit mock preview route. Eventually make `app-v2.html` the opt-in real v2 route. Do not change Welcome/default routing until D9.
2. Create all named shell/scientific hosts and required controller DOM contracts **before** the real bootstrap's first DOM lookup. Register one domain/view owner; keep scientific nodes and real toolbar buttons stable.
3. Use one bootstrap to create state/services/controllers; bind once; initialize scientific adapters once; then restore/start through existing transaction owners. Navigation only shows/hides mounted domains. Never import unmodified legacy `app.js` into the v2 empty shell: it constructs the legacy Workstation, binds it, and asserts legacy rail/stage selectors.
4. Keep `appReady` separate from project/History restore and first complete 3D frame. Maintain the original two sessionStorage keys. A D1 run must prove real hosts/button identity, no double bindings, real pointer/ROI results, overflow/focus/overlay behavior and comparison against M1.5 at all four widths.

Alternative: retain `ui-v2/app.html` as the sole experimental production route while `app-v2.html` remains preview. This reduces immediate route churn but leaves two v2 URLs with different capabilities and postpones public-entry convergence. The recommended choice keeps the existing public v2 path as the eventual product route.
